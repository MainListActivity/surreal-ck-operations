# 公司系统版本与老板收件箱升级

公司使用语义版本号（首次 `v0.2.0`），提交 SHA 同时保留。`package.json.version` 与 `company-release.json.version` 必须一致；每次公司系统上线应提高版本号，并在同一 main 提交中维护标题、上线内容 changes、影响范围 impact、数据变化 migration、回退方式 rollback。版本说明来自待部署提交，老板点击后不能被另一个说明替换。

工程将公司仓库 release/deploy 任务交老板时，使用：

```
sck call report_blocker '{"to":"owner","text":"公司系统版本已合入 main，升级内容与影响已列入版本说明，等待老板点击升级。","companyUpgrade":{"sha":"<完整 main SHA>"},"idempotencyKey":"<唯一键>"}'
```

`submit` 交 owner 关口时同样支持 companyUpgrade。文件入口可独立一行 `companyUpgradeSha: <完整SHA>`。服务端校验当前工程租约、代码仓库、任务阶段和 main 归属后，把该提交的说明与摘要写进任务。普通产品仓库、任意附件脚本或标题里的“上线”不会取得本机升级能力。存量待办无结构化版本时保持原回复入口，工程补齐后使用升级卡片。

Paseo 收件箱与老板网页审核台共用后台，展示当前版本、目标版本、四类清单和提交详情。老板只点“升级至 vX.Y.Z”，不填写回复、不运行脚本。按钮启动持久化作业，连续点击复用同一个在途作业；全公司同时只执行一个升级。已登记公司版本的待办不参与 JEV 自动分流或上线批准，后端事务也拒绝陈旧调度快照改派或自动通过。

后台只调用标准工具，流程为：核目标 main / 版本前进 → git archive 固定快照 → 安装锁文件依赖 / vendor → 类型检查及本机双门禁 → 重核待办版本与现役版本 → 短暂停止新派工 → 标准 company-service.sh install 双面切换 → 核 active、健康/ready、插件来源、schema/vendor、内容与门禁 → 自动回复。不会运行员工附件中的安装脚本。

升级作业由独立进程组执行，插件替换不会终止它。状态与授权写入 company_upgrade / audit；日志在服务目录 upgrades 下。进程异常退出后，只有确认整个作业进程组已消失才标失败；超时杀掉整个组，不让孤儿安装程序与重试并发。错误保留待办，不写“通过”。验证失败尝试用目标守卫恢复前一固定发布；无法证明已恢复时保持暂停。用户在期间手动改变暂停状态时，不由后台覆盖。

成功后：老板待回问题自动 `reply`；老板审核关口通过现有 `approve` 评估器，仍检查验收条件及任务版本。不会代替员工独立业务 QA。若已上线但任务被别人处置或验收条件不足，作业显示“已升级，自动回复待完成”，不强制验收、不覆盖新决定。

041 仅新增作业表与索引。旧版仍可读取既有任务。首次接入可由获授权本地会话用同一作业服务启动，后续使用收件箱按钮。首次发布需验证真实工作进程在插件重载后继续，并完成版本核验与回执；隔离 fork 覆盖重复点击、陈旧任务、失败不放行与暂停状态。
