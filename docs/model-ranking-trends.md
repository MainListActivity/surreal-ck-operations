# 模型排序的趋势事实

排序仍由 JEV 完成，老板规则优先，Opus/Fable 保持手动。每次后台排序前读取 Magpie 的原生7天汇总与本机 usage.jsonl；请求路由不等待采集、数据库或 JEV。

每个完整供应商/模型通道分别提供首 token 延迟、生成速度、错误率、缓存命中率、首 token 超10秒比例。生成速度移植 Magpie usage.Record.DecodeOf 的计时、思考与突发释放排除规则，不使用总输出/总耗时。错误率包含没有首 token 的失败，未计时速度未知。缓存趋势是每请求命中比例；原 usage.cacheHitRate 仍是 token 加权比例。

所有指标（含最终验收绩效、AA智能分/名次、额度、输入/输出/缓存价格）使用同一结构：最新有效值、时间加权EWMA、每分钟斜率、启发式突变、7天基线、窗口分布、样本单位与新鲜度。

- EWMA：请求取最近1小时最多20条、半衰期5分钟；稀疏的任务/变动快照取最近7天最多20条、半衰期24小时。指数时间权重平均，防止历史高流量压倒最近变化。
- 斜率：同一批样本对真实时间做最小二乘回归；至少5条、覆盖1秒，重复时间不伪造斜率。
- 突变：最后10条分为前后各5条，均值变化超过25%、前批3倍标准差与单位最小阈值，后批至少4条同方向。它是启发式提示，不是显著性概率；不触发不代表稳定。过期或无法按时间区分的批次不报告突变。
- 可信度：近期最多20条、至少5条、覆盖1秒；请求最新不超过15分钟，稀疏任务/变动快照最新不超过7天。稀疏/过期数据降权；没有样本不当成零延迟、零错误。
- 窗口：15分钟、1小时、24小时、7天，提供样本数、均值、最近秩P50/P90。
- 绩效：只取最终done任务的评分，同任务多员工/别名记录按原评分权重归并成一个任务样本，非请求次数。
- AA、价格、额度：本地600权限文件只记数值变动；相同值重复读取不制造证据。初次部署没有变动历史时如实标记不足。窗口起点、最后变动时间与采样单位可供JEV判断。

字段字典、单位、计算口径和可信度说明随每次JEV请求发送。没有明确口径的老板阈值保持原usage平均值口径，不擅自改成P90、最新一次或EWMA。排序输入/输出快照保留趋势数据，Paseo和网页审核台使用同一说明文案。

读取日志失败时，原生API汇总仍可用，趋势标记不可用；采集只保留时间和数值，不持久化账号、会话、请求内容或凭证。


## JEV 输入预算与无损列编码

JEV官方文档 https://docs.typesafe.ai/models 规定默认state加任一问题32k token、state加所有问题64k token。逐模型重复完整趋势对象会超过这个限制，真实接口曾返回400 max_tokens_exceeded。

传输时共享一次字段列名、单位和样本单位字典，各指标使用10列数组：current、ewma、slopePerMinute、change、baselineMean、baselineSamples、samples、lastSampleAtMs、ageMs、sufficient。保留全部关键趋势数值；null明确表示未知。窗口分布与完整命名对象保留在成功评分快照和两端UI，首次请求的旧兼容显示可重建关键字段。

本地以state 48000 UTF-8字节、完整请求128000字节进行保守工程预检（不是token计数器），超限不调用JEV、不截断老板规则或丢模型，保留原排序。仍然每组一次调用，不启用实验长上下文。JEV的结构化错误码会进入本地诊断，便于区分输入超限与无答案。

## 持续报错的成员不参与 JEV 排序

Magpie 原生 usage（`/v1/magpie/usage`）只记录最终给出回答的那一次尝试。某个成员被拒绝后请求会转给下一个成员，这次失败不会出现在 usage 里。例如 `remote-magpie/sn/deepseek-v4.1-flash` 返回 403（订阅不提供该模型），usage 里却看不到它报错，JEV 因此按智能分把它排在 Haiku 前列。

现在 `src/model-routing/health.ts` 改为读取 Magpie 路由日志 `~/.config/magpie/routing/*.jsonl[.gz]` 里的每一次尝试：

- 同一个 route id 会被记录多次，只取最后一份。按完整的“供应商/模型”路径统计，不借用其他供应商的数据。
- 未完成的尝试和员工自己取消的请求（499）不计入。

满足以下任一条件的成员由代码判为不可用（`health.excluded`）：

| 原因 | 条件 | 记忆时长 |
|---|---|---|
| `unavailable` | 最近一次尝试返回 401/402/403/404，即无权限或订阅不提供 | 24 小时窗口内，直到再次成功 |
| `consecutive_errors` | 至少连续 3 次失败（429、5xx、断流等），且最近一次在 30 分钟内 | 30 分钟冷却 |
| `error_rate` | 最近 1 小时至少 5 次尝试，失败占比 ≥ 50% | 1 小时 |

被判为不可用的成员不发给 JEV，置顶也不再生效，按现有顺序排到组末尾，也不会显示 JEV 分数。

- JEV 失败，或组里没有其他可评分的成员时，照样把它们移到末尾；最新故障观察独立保存在 `gates`，上次成功的评分、规则与时间保持不变。
- 排在末尾的成员很少再被尝试，所以暂时性错误有冷却期：冷却期过后它重新参与排序，再连续失败就会再次被移到末尾。
- Paseo 排序页和网页审核台都会显示“路由尝试”一栏，写明失败次数、原因和最近一次 HTTP 状态；被移到末尾的成员在分数位置显示“持续报错”。


## 共享输入与预算诊断 v2

排序输入构造与兼容解码集中在 `src/model-routing/ranking-input.ts`。完整老板规则与优先级说明只在共享state写一次；每题引用该规则和模型编号，五档criteria仍逐题提供简短的具体条件。账号列表、来源元数据、相同趋势行以组内 `$ref` 复用，每个请求自带完整 `refs`，没有跨请求依赖。

默认 `shared-v2` 保留模型对象字段；共享state或完整请求超过原预算70%时，改用 `columns-v2`：模型按 `factColumns`、趋势按 `metricColumns` 的列顺序编码，字段和模型一项不删。两种编码都保留最新值、EWMA、斜率、突变、基线、样本量、时间与充分性；只有数值精度规范化到最多4位小数（价格8位），计数和时间戳不变。详细窗口与原始精度仍在成功评分快照。旧v1请求及两种v2均可解码供首次/历史页面显示。

预算仍为共享state48000 UTF-8字节、完整请求128000字节；不是token计数。超限时不调用、不拆批、不删模型、不截老板规则，保留成功排序，故障成员仍由代码移到末尾。每组保存最近一次 `attempts`：时间、编码、评分模型数、两个实际字节数与限制，以及 prepared/success/budget_exceeded/upstream_error/invalid_answer 状态。预检拒绝也有记录，实际调用快照仍仅代表发送前的完整请求。两端页面展示尝试预算和明确的超限原因。

最新 `gates` 只用于故障状态、末尾门禁与未评分成员的实测事实；成功成员的JEV评分及其指标仍来自同一成功快照。刷新失败不覆盖 `results`，避免清空全部正常模型的分数；页面分别标注最近刷新尝试与最近成功评分的时间。
