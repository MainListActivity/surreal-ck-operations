# 任务生命周期与交接

## 任务模型

一个业务目标是一张 `kind:outcome` 主任务，由 product 或 gm 对最终结果负责；每个阶段是一张 `kind:task` 子任务。缺陷、事故和经常性运营也使用同一模型。正文用父任务、依赖和后续任务链接表达关系，首版不依赖 GitHub Projects 或原生子任务功能。

一张阶段任务包含：目标、原执行人、当前处理人、验收人、下一角色、输入、交付位置、逐条验收条件、依赖、后续任务、优先级和截止时间。验收人是下一次操作的责任人，下一阶段负责人不一定是同一个人。

原执行人负责成果直到验收通过；GitHub assignee 始终指向当前要采取动作的人。待验收时 assignee 转验收人，原执行人留在正文。客户目标主任务只有在客户结果验收后才关闭，代码合并不关闭客户目标。

## 状态与允许动作

每张公司任务只能有一个 `state:*` 标签；更新状态时先移除旧标签，再添加新标签。

| 状态 | 进入条件 | 当前处理人 | 下一步 |
|---|---|---|---|
| inbox | 新请求已记录 | gm / 值班分诊人 | 澄清、拒绝，或拆出 ready / blocked 阶段任务 |
| ready | 执行人、验收人、输入、条件、截止和权限齐全；依赖全部验收通过 | 执行人 | 接单转 doing |
| doing | 执行人确认领取且有产能 | 执行人 | 提交转 review；缺输入转 blocked |
| review | 交付单与证据完整，验收人真实且有访问权限 | 验收人 | 通过转 done；不通过退回 doing；需外部输入转 blocked |
| blocked | 缺材料、权限、人员、决策或上游结果 | 负责解除阻塞的人 | 条件补齐后恢复先前阶段；正文记录恢复目标、原执行人和期限 |
| done | 独立验收通过，后续任务已建立并分派或明确“无后续” | 无待动作；保留最后验收人 | 关闭为 completed |
| cancelled | gm 决定终止并记录原因、数据处置和依赖影响 | gm | 关闭为 not planned；下游不能视作已通过 |

`priority:P0/P1/P2` 是业务优先级；`role:*` 是当前处理人岗位。待配员是附加标签，不是执行状态。父目标在子任务执行期间保持 doing；不计入个人两项执行 WIP，但每位目标负责人最多同时推进三个目标。

## 提交与接收：顺序不能省略

**执行人提交：**

1. 将成果保存到任务规定位置，检查验收人能访问；写交付单，逐条链接验收证据、版本与已知限制。
2. 确认下一阶段任务已存在并链接当前任务为依赖；若需动态分支，先创建 blocked 后续任务。无后续写明原因。
3. 将 assignee 和 role 转为指定验收人，状态转 review，登记提交时间和验收期限。保留原执行人。
4. 无法设置 assignee/labels 时，保留当前责任，在原任务记录阻碍并交 gm 协助；只写评论不视为交接成功。

**验收人处理：**

1. 检查自己是否独立且有权限；不适任时由 gm 指定替补，不自行通过。
2. 按原条件重现、抽验或核对全部必要证据。记录通过项、失败项和证据，不能只写“LGTM”。
3. 退回：写出失败条件、复现方法和期望结果，任务转原执行人、doing；如果输入前提改变，则交 product 变更范围后重排。
4. 通过：写验收单；关闭当前任务并标 done；逐个检查后续任务的**全部**依赖，只有都 done 且证据通过、人员权限齐备才转 ready。取消的依赖不算通过。
5. 为后续任务填入本次成果链接、真实 assignee、验收人和期限。更新父任务进度；最后一个阶段通过时由目标负责人做整体结果验收。
6. 写明“已解锁 #编号 / 仍阻塞 #编号及原因”。中途操作失败时保留一条交接未完成记录；由经理检查台补齐。GitHub 多任务更新不具备事务性。

重复提交在原任务追加新版本，不创建相同任务；重复验收先检查已关闭状态与后续任务，补遗漏，不重复建票。版本改变后旧测试结论不自动覆盖新版本，必须说明复用范围与新增验证。

## 阻塞、超时与变更

- 阻塞单必须写“谁在何时前提供什么、完成后恢复哪张任务/哪个阶段”。缺少解除人时立即交 gm；阻塞任务的 assignee 是解除人。
- 默认工作日内：新请求 1 个工作日分诊；ready 任务 1 个工作日接单；review 1 个工作日响应；doing 每个工作日留一次结果/下一步/阻塞更新。
- 所有期限使用 ISO 日期时间与时区。gm 在启用任务确认工作日、营业时间和节假日后启用 SLA，未确认前不宣称全天候响应。
- 截止时间将到或已过，当前处理人先记录影响与建议；gm 每天两次检查，超时一个工作日指定替补或调整范围与期限。GitHub 不会自动升级。
- 客户改变范围：product 建立变更任务，说明新增价值、费用、工期及原验收条件的变化；gm 批准后更新关联任务。员工不得用口头要求静默替换原验收。
- 原工作完成后出现新问题，建立关联缺陷；交付未达原条件则在原任务退回。P0 事故进入下面的快速路径。

## 事故快速路径

数据丢失、越权、关键流程全面不可用等列为 P0。发现者立即建 `kind:incident`，在已批准值班渠道通知值班人；没有值班安排时不能承诺 24×7。

qa 任事故协调者，engineering / ai-content 按影响范围处置，cs 按批准口径联系受影响客户，gm 决定暂停交付。先保存证据、隔离影响或执行已授权恢复，再定位修复。修复由独立人员复验，product 确认业务恢复；恢复后 2 个工作日内提交复盘与防复发任务。补丁仍需关联版本、验证与恢复方案。

## 与研发工单的边界

技术 PRD 与细分规格继续在产品仓库 `.scratch/<feature>/`；本库任务链接具体文件和固定提交。公司阶段状态只在这里维护，不复制所有历史研发工单。

公开 PR 只关联可公开技术内容，不写客户、合同、公司内网链接或私有运营摘要。本库任务链接公开 PR。代码使用“关联 / Refs”，公司验收不依赖 PR 的自动关闭行为。`.scratch` 的 done 代表其技术条件完成，不替代客户验收或商业上线。
