# 实现人绑定、独立复核与无法派工（SYS-DISP）

本文件说明工程任务的执行与复核规则、无法派工的可视化，以及经理接手与只读核对的操作方法。规则在核心（`src/core.ts`）、
退役门禁（`src/retirement.ts` 与 `src/workforce.ts`）、调度器（`src/dispatcher/dispatcher.ts`）和推导模块（`src/contributors.ts`）中强制执行，提示词与偏好只作说明。

## 一、规则

- **作者**：提交过任务的人，或持有过执行阶段租约的人（认领、检查点、阻塞、释放）。作者身份永久保留，退回、撤销或改派都不会移除它。
- **复核人**：在复核阶段持有过任务、且不是作者或实现人的人。复核、退回、验收都不会使其成为作者，它可以重复复核，但不能实现。
- **实现人**：首次执行阶段认领时绑定（`task.implementer`）。退回默认回到实现人修复，保留其登记分支与现场。
- **独立复核**：`accept`、`return` 与复核阶段的认领，对全部作者与实现人一律拒绝，不只看最后一次提交人。
- **开放租约**：当前持有人的租约若尚无决定动作，其行按任务当前阶段计（复核阶段计为复核人）。这保证复核人能完成自己的复核。
- **历史不清**：旧行缺少阶段且之后没有可判定的决定动作，按作者处理（fail-closed），并在结论中列出该行数量。
- **并发**：推导视图与任务版本同读于一个事务。租约写入在 SQL 内比对版本，视图已变则重读重试；连续失败返回 `conflict`，不写租约。
- **退役硬门禁**：所有退役与撤凭证都经同一边界 `gateCredentialChange`（判定与写入都在 `src/retirement.ts`）。退役经 `Workforce.retire`（`admin retire`、调度器各退役点与场景回收），撤凭证经 `LocalEnrollmentAdmin.revoke`（`admin revoke`，安全撤销）。插件内的调度依赖也调用同一函数（随 vendor 重生成生效）。下列员工一律拒绝，且拒绝先于任何写入：
  - 仍持有任一任务的有效租约（任何阶段）：`active_lease`；
  - 是未结束任务（非 `done`、`void`）的显式实现人，包括返修（`ready`）、待复核（`review`）与阻塞（`blocked`，依赖或经理等待）：`bound_implementer`；
  - 旧任务缺实现人字段：是唯一派生作者时为 `legacy_implementer`，多作者且无实现人时为 `implementer_unresolved`。无法判定阶段的旧行按作者计。

  不拒绝：只参与过复核、既不是作者也不是实现人的人；`done` 或 `void` 任务上的历史作者。作者身份永久保留，退役也不移除。

  拒绝返回稳定错误码 `retire_refused`，附涉及的任务、阶段、状态、原因与合法动作（多条动作以 `1）…；2）…` 分隔）。`admin retire` 与 `admin revoke` 输出 JSON 并以退出码 1 结束。门禁拒绝时不写入：凭证、退役标记、安全撤销标记、租约、围栏与任务版本均保持不变（调度器在工作区变化分支中先于门禁释放租约，见 §六）。没有 `force` 或其他旁路。

  接受的退役或撤凭证在同一事务内重算在办关系，并与决定时的候选集合及版本逐一比对；并发移动或提交冲突按决定重试，重试耗尽返回可重试的 `temporarily_unavailable`。认领与接手同事务写员工记录，因此与退役或撤凭证冲突，不会同时成功。撤凭证保留 `security_revoked`，不写退役标记，因此不会被当作可自动复活的普通退役。
- **自动会话轮换**（调度器替换旧会话）同样经门禁：持有人与绑定实现人被拒绝时，本轮不轮换（`src/dispatcher/dispatcher.ts` 轮换段）。历史不可读时整轮不轮换。凭证轮换（`Workforce.rotate`）不在此门禁内，见 §六。

## 二、经理接手（`implementer_takeover`）

仅 gm 可用，需要 `manage` 能力。条件与写入都在一个比较并交换的事务里完成：

- 任务处于执行阶段（`ready`、`doing`、`blocked`），`expectedVersion` 与当前版本一致；
- 目标员工具备执行能力、岗位与轨匹配；若目标是当前复核人，必须同时指定独立的 `replacementReviewer`，且它不是任何作者；
- 理由不少于 8 个字符，幂等键相同且载荷相同则返回原结果；
- 写入审计、出站事件与幂等记录；原持有人的租约被撤销（围栏前进），作者记录不被删除；
- 目标员工记录同事务写入 `implementer_bound_at`，使接手与对该员工的退役互相冲突，不会同时成功。

**实现人已不可用时的自动接替（不经经理）**：绑定的实现人——显式绑定，或由贡献记录派生的唯一作者——彻底不可用时（员工已退役/撤凭证、不在册，或会话被归档、隔离、停在无法就地重启的失败里），调度器在下一轮 tick 直接把执行权交给同仓库、非作者的在岗工程员工。写入与经理接手是同一笔比较并交换事务（版本、目标岗位/能力/轨校验，原租约撤销、围栏前进，作者记录保留），只有 actor 不同：审计记为 `system:dispatcher`，事件标记 `[implementer_takeover:auto]`。实现人只是忙、空闲、额度冷却或状态未知时不触发，等它自己恢复。没有可派候选时任务按 `implementer_unavailable` 记为无法派工，负责方是「系统」，每轮自动重试，不占用经理。

接手不是老板批准，也不替代上线决定。需要花钱、扩编或换供应商的事项，仍须经老板或经理按既有流程处理。

### 退役或撤凭证受阻时的安全恢复

退役或撤凭证被拒绝时，员工、凭证、会话与租约都原样保留。按下列顺序处理，不直接改库：

1. 等待在办任务结束（完成或作废）。租约过期或被调度器收回不解除员工与任务的关系：实现人绑定与作者记录都保留，退役仍会被拒绝，直到任务结束或经理接手。
2. 需要提前退役时，执行阶段（`ready`、`doing`、`blocked`）的实现人可由经理先用 `implementer_takeover` 交接给其他具备执行能力的工程员工（条件见上文，作者记录保留）。目标若是当前复核人，须同时指定独立的替代复核人。
   复核阶段（`review`）不能接手，拒绝说明会写明“等待复核完成”。复核租约没有受权的提前释放入口，释放它也不解除实现人绑定。退回到执行阶段后，才可按本条办理。
3. 旧任务缺实现人字段时，先用 `contributor_dryrun` 核对贡献记录与时间线，再用 `implementer_takeover` 记录唯一实现人（执行阶段）。
4. 处理后重试退役或撤凭证。每次拒绝都会列出仍需处理的任务、阶段与合法动作。

拒绝时调度器不归档、不解绑、不重派：tick 报告的 `refused` 列出该实例。场景回收（`createSceneCleaner`）逐个退役工作树内的员工。遇到任何未完成的员工退役（拒绝或其它失败），该员工的会话保留：不解绑、不归档；同一工作树内已完成退役的员工照常解绑并归档。随后本树的工作区与项目一律不拆除，抛出可重试的 `temporarily_unavailable`（`scene kept: employee retirement not completed for …`），登记的 `cleanup_todo` 记为 `scene-cleanup-failed:scene kept: …`（含原因），后续扫描会重试。

## 三、只读核对（`contributor_dryrun`）

仅 gm 可用。输入至多 20 个任务号，输出每个任务的状态、版本、当前持有人、上次提交人、作者、复核人、已排除的人、
实现人状态（`bound`、`proposal`、`manager_decision`、`fresh`）、建议（只建议，不写入）与逐事件时间线（每行的角色与阶段来源）。
它不改变租约、提交人、老板门、历史或实现人。

## 四、无法派工的可视化

同一评估器（`src/dispatcher/dispatch-blocked.ts`）产生调度器、通知、花名册、队列与目标卡的结论。每个结论包含：

- 任务、目标、阶段（执行或复核）、`checkedAt`、等待起点与已等待分钟数、可派工候选数；
- 全部生效的原因码、涉及的候选、负责岗位（gm 或老板）、恢复动作与下一触发条件；
- 材料性阻塞（无独立候选、作者回避、实现人冲突、状态未知）即时通知；可自行恢复的等待满 5 分钟通知。

通知键为 `dispatch-blocked:<任务号>:<阶段>`，同一阶段的重复 tick 与重启只保留一条未解决项，条件变化时更新文本。
可派工后自动消警（通知记录写入 `resolved_at`）。目标卡显示根阻点，展开可看全部原因、候选与恢复动作。

状态未取得时只能是 `unknown`，不会显示为忙碌。花名册与队列的会话状态来自本轮 tick 的观测，不再二次读取 Paseo。

候选范围与原因文本：

- **仓库硬过滤**：同岗位员工若属于其他仓库，不进入本仓库的候选池：不被唤醒、不获得代码写权、也不计为原因。本仓库有空闲候选或可合法新开的席位时照常派工。
- **零候选摘要**：本仓库没有任何可派候选时，摘要写明被排除的他仓员工数（"另有 N 名同岗位员工属其他仓库，不参与本仓库派工"），原因只列本仓库的席位、额度与写权事实。
- **席位文本**：`编制席位已满（已用/上限 个实例，仓库 <仓库名>）`，写明被占满的仓库。
- **额度**：`订阅额度或健康冷却中，恢复时间 <ISO 8601>`。任一候选的恢复时间无法证明时，整组写 `恢复时间未知`，不推算。
- **探测占用**：冷却已过、单次探测会话尚未结束时为 `probe_busy`（单次探测会话占用中），不写恢复时间，也不冒充并发已满。`订阅并发已满` 只在真实并发满时出现。
- **经理待办**：ready 的 `implementer_unresolved`、系统自动接替无候选的 `implementer_unavailable`、以及绑定实现人持续额度失败（provider 连续失败或恢复时间未知）会进入按仓库分组的经理待办/唤醒。同一 task+阶段+episode+reason 只建一条（dispatch 记录持久化），负责人记录、开工、退役或理由变化时收口，审计保留；读取失败保持待办。GM 先 `contributor_dryrun` 再以最新 `expectedVersion` 调 `implementer_takeover`，ready 任务不要 `resume_task`；普通忙碌、在办租约、普通并发满、依赖等待不升级。
- **实现人失效**：`implementer_unavailable`，负责方写「系统」而不是经理；恢复动作是「系统自动改派，无需经理；暂无候选时等候选人空闲后自动重试」，出现候选后由调度器自行改派并消警。
- **写权冲突**：同线或重叠目录的在办写者占用工作树时为 `write_scope`，责任人为经理，候选写明持有者（任务号前 8 位与员工）。它不产生 `wake_failed`，不进入冷却；写权被占用时不创建会话，也不因此退役已有会话。持有者结束后自动可派工。

## 五、QA 验证（入口 → 操作 → 应见）

以下步骤在公司 fork 的隔离库或受控测试接缝上执行。生产只读核对不得造数，也不得改动任务。

1. 目标卡：打开一个存在无法派工任务的目标 → 应见根阻点一行，写明阶段、原因与已等待时长；展开后应见每条原因、候选与恢复动作。
2. 编制（界面「编制」标签，「员工编制」分区）：有空闲会话、但 tick 观测为忙碌的候选 → 分组标题的忙数计入该候选，不显示异常，且与调度器的判定一致。
3. 复核接力：工程 A 实现并提交 → 工程 B 复核并退回 → 应见任务回到执行阶段、实现人仍为 A；B 不能认领执行。
4. 作者回避：A、B 皆为作者 → 工程 C 复核可认领；A 与 B 认领复核均被拒绝（`self_review`）。
5. 经理接手：gm 对执行中的任务调用 `implementer_takeover`，理由不足或版本过期 → 被拒绝；理由充分且版本一致 → 实现人变更，原持有人租约被撤销。
6. 只读核对：gm 调用 `contributor_dryrun` → 返回作者、复核人与时间线，前后任务版本与审计行数不变；非 gm 调用 → `forbidden`。
7. 通知去重：同一阶段连续 10 次 tick（中间重启一次）→ 同一通知键仅一条未解决项。自动化覆盖的层次见 §六。
8. 跨仓库：本仓库任务没有可派候选，而他仓有同岗位员工 → 无法派工摘要应见"另有 N 名同岗位员工属其他仓库，不参与本仓库派工"；他仓员工无唤醒记录，也无写权。
9. 同线写者：同一任务线已有在办写者 → 等待任务的原因为 `write_scope`，候选写明持有者；持有者提交后该任务可派工，全程不出现 `wake_failed`。
10. 退役门禁：在公司 fork 隔离库中，对持有活租约的测试员工执行 `admin retire` → 应见 `retire_refused` JSON、退出码 1；员工凭证仍有效，租约、围栏与任务版本不变。任务结束或完成交接后重试 → 应见 `ok: true`。生产只读核对不得执行退役。
11. 撤凭证门禁：在公司 fork 隔离库中，对持有活租约的测试员工执行 `admin revoke` → 应见 `retire_refused` JSON、退出码 1；凭证摘要、`revoked` 与 `security_revoked` 不变。无在办关系的员工执行 `admin revoke` → 成功，写入 `security_revoked`，不写退役标记。
12. 场景回收：员工退役遇非拒绝失败 → 应见 `scene kept` 可重试错误；该失败员工的会话未解绑、未归档，工作区与项目未拆除（同树中已完成退役的员工会解绑归档）。

## 六、测试分层与未覆盖

自动化用例按层区分真实与替身。替身层的结论不能当作真实环境的证明。

- **真实**：SurrealDB（公司 fork 二进制、隔离库）、核心（claim、transition、implementer_takeover、contributor_dryrun、审计与版本 CAS）、调度器（`Dispatcher.tick`）、`SidecarPool` 与通信目录的请求和回应。`tests/dispatcher-sidecar.fork.test.ts` 在这些真实层上覆盖：接手后续做、两轮返工、额度恢复与通知消警、老板门、轮换保留实现人、legacy 行 fail-closed。
- **替身**：公司 fork 用例中的 Paseo 网关为内存会话表（状态与最后错误由测试设置，可置为 `unknown`）；`sck` 进程（测试直接写请求并读回应，不启动 sck）；运维工具（桩，只报可用）；额度耗尽由测试注入错误文本。真实 CLI 的契约见下条。
- **Paseo 真实 CLI 契约**：`tests/fixtures/paseo/` 为 paseo 0.12.0 只读采样的脱敏样本（版本、采样时间、命令与退出码见该目录 README）。`tests/paseo-contract.test.ts` 用假 CLI 脚本，经真实 `createPaseoCli` 与 `Dispatcher.tick` 验证：非零退出、非 JSON、超时、空输出与缺少 `Status` 均得到 `unknown`，且不退役、不归档、不派工。只有 CLI 明确返回 `AGENT_NOT_FOUND` 时，会话才视为缺失。
- **10 次重复 tick（含一次重启）**：`tests/dispatch-episode.fork.test.ts` 在公司 fork 真实数据库上运行十次 tick，中间重启一次，直接查库断言通知、任务行、审计行、派工行与 `dispatch_blocked_since`；原因变化时同一条通知更新文本。`tests/dispatcher-sidecar.test.ts` 的 R3 用例仍为内存替身，只作补充。
- **写权预检与认领**：`tests/worktree-registry.fork.test.ts` 的 LANE 用例在公司 fork 上验证：预检报告的持有者与认领的拒绝一致（`worktree_busy`），拒绝时任务保持就绪，持有者提交后预检为空，认领落入同一条线的工作树。
