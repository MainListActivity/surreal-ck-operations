# 线的笔记与一次性会话：设计

状态：老板已确认方向（2026-11-07）。阶段 0、1 在 v0.3.81 上线，阶段 2 在 v0.3.82 上线；阶段 3 已完成，72 条种子笔记已生效，生产已切到 `oneshot`，v0.3.83 修复返工回不到原会话的问题。替代评估时提出的 `context_id` 方案。

> 0.5.0 替代说明：会话归因改为“换任务即换会话”，reuse 与 oneshot 两种策略都是，同一任务内的返工、复审接续原会话。本文的规则 2（紧密相关的后续任务沿用父任务会话）与 `pick` 顺序已不再生效。eval 会话已随 eval 岗位删除。线的笔记、消息与整理机制不受影响。

## 目标

老板手动指挥 agent 时会开 n 个会话，一个写代码，一个出验证清单，彼此隔离。公司派工要得到同样的效果，并且让“项目 1 的质量要求”这类经验长期留存。

做法是把两件事分开：

- **隔离单元是线**：一条线 = 项目 × 职能，例如“项目 1 的 qa”。
- **长期知识存在线的笔记里**，会话只是干活的工作记忆，用完就结束。

依据是 Anthropic 的 Claude Code 指南：新任务开新会话，反复用到的知识写进文件，复核者不要看到实现过程。

## 概念

**线的标识**：`<项目 id 或 company>:<岗位>`。项目取 `task.project`，没有项目的任务归 `company`。执行线用 `executor_role`，复核线用 `reviewer_role`。`reviewerRole=owner` 时老板不属于任何线。

**三层信息**

| 层 | 内容 | 寿命 | 存放 |
|---|---|---|---|
| 线的笔记 | 项目要求、踩过的坑、处理办法 | 长期 | `lane_note` 表，派工时生成 `notes.md` |
| 会话 | 当前任务的工作过程 | 到任务结束 | Paseo |
| 任务 | 需求和验收标准 | 跟任务走 | `task.md` |

笔记由公司系统保存，不用 Claude Code 的 auto memory 或 subagent memory，原因是 factory-droid 和 antigravity 也要用，且老板要能在控制台看和改。

## 线的笔记

**数据**：新表 `lane_note`，一条经验一行。

| 字段 | 说明 |
|---|---|
| `lane` | 线的标识 |
| `text` | 一条经验，不超过 240 字 |
| `state` | `proposed`、`active`、`removed` |
| `phase` | 提议来自执行线还是复核线，退回时用来区分 |
| `source_task` | 来源任务，老板手写时为空 |
| `by` | 提议者，老板手写时为 `owner` |
| `pinned` | 老板置顶，排在最前 |
| `created_at`、`updated_at` | 时间 |

**读**：`sidecar.claim` 在写 `task.md` 的同时写 `notes.md`，内容是这条线全部 `active` 的条目，置顶在前，其余按时间倒序。每条线之间互相不可见，所以执行线看不到 QA 的笔记。

**写**：`submit` 和 `review` 增加可选参数 `learned: string[]`，最多 5 条。

- 写入时状态为 `proposed`。
- 调度器每轮结算：任务 `done` 的转为 `active`，`void` 或已删除的丢弃。所有结束方式走这一条路径，最多晚一轮生效。
- 任务被退回时，同一事务里丢弃执行线的提议，复核线的提议保留。这样被否定的做法不会进笔记。
- 老板手写和修改立即生效。
- 写入前检查常见凭证格式，命中就拒绝这次提交。客户资料无法靠规则识别，靠老板审阅。

**上限**：`notes.md` 不超过 200 行或 25KB，与 Claude Code 的 `MEMORY.md` 一致。超限时新条目继续留在 `proposed`，不生效，并给老板发一条提醒。每条线的生效笔记（含置顶）最多 30 条，到顶后新提议同样排队。

**整理**：笔记不随时间一直涨，由系统定期自动合并清理，老板无需手动删减。

- 相似度（字符二元组的 Dice 系数）不低于 0.5 的生效笔记合并。相连的一组（A 像 B，B 像 C）整组合并，保留最近更新的那条，其余转为 `removed` 并记下 `merged_into`。这个阈值比去重的 0.6 宽，因为这里要合并的是同一条经验写了两遍。
- 合并后，一条线的生效笔记仍超过软目标 20 条时，按更新时间从旧到新清理非置顶的笔记，原因记为 `aged_out`。置顶笔记计入数量但不动，`proposed` 也不动。软目标比上限 30 低，整理后一般能留出余量给之后的新笔记。
- 生命周期整理每 30 分钟检查一次，每 24 小时对全部线整理一次，actor 为 `system:consolidation`。老板可用 `note.consolidate` 整理一条线或全部线，传 `dryRun` 只看计划、不写库。
- 每次实际改动都写一条整理记录，逐条保存改动前后的状态和文本。`note.consolidation.undo` 或控制台的撤销按钮能把这次改动全部恢复。撤销时，之后又被改过的笔记保持现状，并列在撤销结果里。同一次整理只能撤销一次。

**内容规则**：笔记记标准、方法和坑，不记某次任务的结论和实现思路，否则会削弱复核的独立性。这条只能写进消息模板要求，不能强制，所以老板的可见可改是最后一道保障。

## 消息

- 执行、返工、复核的草稿生成时加上“先读 notes.md”和 `learned` 的用法，路由表的自定义正文同样追加。存进表里的就是完整正文，预览和实际发送一致。
- 0.13.11 起正文不再是固定模板，而是由任务卡组装的三段：做什么（任务说明）、可以用（任务卡的 `resources` 加 notes.md 与工作能力目录）、验证（验收标准加一句收尾约定）。任务卡是事实来源：`task.update` 后，未发出且老板没改过的草稿自动重算（草稿上的 `composed` 标记）；老板改过的草稿、路线与需求流水线的自定义正文不动。说明或验收超过 6000 字时该段改为指向 task.md。收尾约定（首行“复核结论：通过/退回”“工作结果：受阻”）是执行端 `workResult` 的判定依据，完工分析上线前不能删。实现见 `src/outbound-render.ts` 的 `composeMessage`。
- 0.13.13 起：老板答复受阻任务后，恢复派工的消息最前面带上受阻原因和老板原话（`latestAnswer`），并落成 `answer.md` 供云端与网页通道内联；发出前按任务卡和最新进展重算一次没改过正文的草稿。完工分析（`src/turn-analysis.ts`，表 `turn_analysis`）只记录并在任务详情展示：它不改消息、不决定流转，流转仍只认答复首行的结论。
- `renderMessage` 把 `notes.md` 补成绝对路径。
- 控制台新增“线的笔记”页：按线浏览、编辑、置顶、删除，并显示待生效条目。任务抽屉里显示这个任务的会话将读到的笔记。

## 会话规则

**选会话**：`pick` 改为下面的顺序。

1. 同一任务同一阶段的会话继续：返工、老板答复后恢复、再次复核都走这条。判定是会话的 `last_task` 和 `last_phase`。
2. 紧密相关的后续任务，沿用父任务的执行会话。判定条件：会话的 `last_task` 是父任务、`last_phase` 是执行、线与本任务相同。第一个子任务领取后 `last_task` 就变了，后面的兄弟任务自然开新会话。
3. 其余情况开新会话。

会话不可用（额度、故障、已结束）时一律开新会话，靠笔记、`task.md` 和交接包继续。provider 选择不变。

**结束**：任务终态（`done`、`void`）后，这个任务的会话在下一轮回收，除非规则 2 要沿用它。`employee` 在领取时记下 `lane`、`last_task`、`last_phase`。

**提交后结束回合**：会话运行中就算不可用，所以派工消息要求提交后结束本轮，否则返工回不到原会话，还会空转。

**工作区**：Paseo 工作区是装会话的容器，一条任务链一个，用根任务标题命名，id 记在根任务的 `paseo_workspaces`，会话记在 `paseo_workspace`。链上任务全部结束且没有在册会话时归档。没有任务的会话放在“日常维护”。

**上下文超限**：沿用 `sessionMaxInputK`（200K）。只在没有租约时生效，下一步按新会话处理，不打断进行中的任务。

**席位**：现在等待复核的会话也占 `maxInstances` 席位，一次性会话下 `qa-claude` 和 `product-claude` 这种 `max=2` 的定义很快会 `seat_full`。席位改为只计算持有租约或运行中的会话，宿主机总量仍由 `maxRunning` 保护。

**独立性**：路由表已保证执行岗不等于复核岗，`prior_submitters` 的检查保留。

**回滚**：`sck owner session.policy` 设置 `oneshot` 或 `reuse`，出问题时切回 `reuse`。

## 种子笔记与存量会话

历史任务已清空，存量长会话里的项目经验目前只存在于这些会话中（数据库备份有任务正文，但没有这些总结）。

阶段 3 先给唤醒 10 次以上的会话（eval 岗位会话已随岗位删除，不计入）各发一条消息，让它写出可长期复用的要求和坑，共 12 个。写入时为待生效状态，老板在控制台审过后才生效，再回收这批会话和其余孤儿会话。这些会话的 goal 范围要先对照备份确定属于哪个项目。

## 验收

- 新任务默认开新会话；返工回到原会话；符合规则 2 的子任务沿用父任务会话。
- 不同项目的同一岗位读不到彼此的笔记；同项目的执行线读不到复核线的笔记。
- 被退回后作废的任务，`learned` 不进入 `notes.md`；`done` 后才生效。
- `notes.md` 超限时不再增长，老板收到提醒。
- 消息表里的正文和实际发送一致，控制台能看到将要读到的笔记。
- factory-droid 会话能读 `notes.md`、提交 `learned`。
- `max=2` 的定义在多个会话等待复核时，不出现 `seat_full`。
- 切回 `reuse` 后派工行为恢复。
