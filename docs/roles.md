## 各岗位每天从哪里取什么工作

岗位公共池查询：`is:issue is:open label:role:<岗位键>`。已分派员工只需使用 README 的 `assignee:@me` 链接。每张任务只保留一个当前岗位标签和一个当前 GitHub assignee；原执行人与指定验收人在正文长期保留。

| 岗位 | 输入来源与可领取任务 | 产出与提交位置 | 谁接收验收 | 权限边界 |
|---|---|---|---|---|
| gm | 新请求池、升级任务、每周经营数据 | 分诊决定、批准范围、经营复盘；原 Issue 评论 / docs 决策文件 | 公司负责人验经营决策；下一角色确认可执行性 | 可排期调配；超预算、合同与用人承诺交公司负责人 |
| product | 已批准商机、客户反馈、已验收版本 | 场景说明、验收样本、交付报告；规格放产品仓库 `.scratch`，业务成果留本库 | gm 验范围；qa 验可测性；cs 接收交付包 | 定义业务口径，不能替代独立法律复核 |
| engineering | 已批准且依赖完成的开发任务、qa 退回缺陷 | 产品仓库 PR、变更说明、验证和恢复证据；本库原 Issue 交付单 | ai-content 做适任代码复核，qa 验行为 | 按现有架构开发；生产动作需明确授权 |

| qa | 产品规格的可测性检查、开发提交、发布候选、事故 | 测试报告、缺陷、风险与发布建议；原 Issue 或缺陷子任务 | product 验业务结果；gm 收发布建议 | 可阻止不满足门槛的发布；自己的修复由其他人复验 |

代码复核与业务验收分开记录；执行人不验收自己的产出。若人员不足，经理指定替补或保持阻塞，不能把缺少独立验收隐藏为已完成。

## 员工入职操作

1. 公司负责人批准岗位、人员与预算；gm 更新人员登记并配置最小仓库权限。
2. 员工阅读 README、自己的岗位行与 workflow；使用脱敏演练任务完成一次“领取—提交—退回—重交—通过”。
3. gm 确认员工能打开自己的四个队列、访问交付材料；将该岗位待配员任务逐项改为真实 assignee。
4. 检查每张任务依赖：齐备则 ready，未齐备保留 blocked；记录到期时间、验收人和替补。
5. 离岗或休假时 gm 转移未结任务、验收责任与授权，保留历史执行人；撤销不再需要的访问。
