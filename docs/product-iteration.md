# 产品迭代闭环

目标：反馈进入需求池，老板编辑并确认开工，执行端拆任务、交付、发布并验证上线。状态保存在云端；不依赖某个常驻 Claude 会话，不新增独立定时器，使用现有 Worker 唤醒与执行端循环。

## 数据与授权

- product_iteration：关联既有 project 的反馈入口及发布策略。补充说明只能由老板修改；开工确认即授权独立复核后的 PR 合并，GitHub CI/CD 自动部署。旧 autoRelease 字段仅兼容历史快照，不再形成二次审批。
- product_feedback：保留原始反馈、来源、分类及关联需求。反馈是外部数据，不是执行指令；不能携带公司执行凭证或指定任意部署地址。
- product_requirement：独立需求草稿，带 revision。编辑使用乐观锁，拒绝覆盖已被其他窗口修改的内容。实施后的范围变化先暂停并重新确认。
- requirement_approval：老板确认的不可变快照，包含需求及当时的产品发布策略。只有老板数据库身份能写入；agent、执行端和自动整理不能代签。
- 任务仍使用既有 task、租约、评审和验收链。需求通过确定性 idempotencyKey 建立规划任务；崩溃后可重试，不能重复拆出根任务。

## 状态

需求：draft（待整理）、pending（待确认）、queued（已确认待规划）、implementing（实施中）、release_pending（合并与上线核验中）、released（已上线）、paused（暂停）、rejected（拒绝）、merged（已归并）。

反馈：new、processing、linked、dismissed、failed；误判可由老板恢复。整理失败保留原文，不自动开工。

上线必须关联已确认修订、任务验收、发布提交/版本和验证证据；通过 CI 不等同于上线。未核验实际部署与独立 QA 线上验收时不能宣称已发布。

## 实施与验收顺序

1. 需求模块、数据库迁移、老板命令与需求页；验证未确认不能启动、并发编辑冲突、重复确认幂等。
2. 反馈组件、公开接收接口、来源约束与限流；自动分类去重形成草稿，老板可查看原文。
3. 确认快照接入规划任务、任务树和执行端恢复；需求页显示任务、阻塞和证据。
4. 产品发布策略与发布观察，挑选明确授权的测试产品验证完整链路。
5. 公司 fork 集成测试、Worker/插件构建、CI 和正式发布；验证生产测试需求与反馈，记录验证边界。

本文件是实现设计，不改变员工执行规则。上线前全部新增入口须经过真实身份与失败路径测试。

## 当前实现约定

- 反馈使用 Web Component：老板端“用户反馈”区域提供每产品嵌入代码。公开接口 `POST /api/feedback/:project` 只返回收件号，不返回需求或其他用户资料。允许来源不等于用户认证；接口另按每 IP/产品每小时 20 次、每产品每小时 1000 次限流，单请求 32 KB。请求键幂等；联系方式不送入模型。
- 现有每分钟 Worker 唤醒最多整理 3 条反馈、规划 1 条已确认需求；有期限的认领与最多 3 次模型重试。失败保留内容，可由老板重试。候选去重限制为最近 30 条需求，无法保证跨全部历史的语义去重。
- 结构化计划限制为 1–6 步。先由产品岗核对计划、QA 复核，再按顺序派工程任务，每步 QA 独立评审。实施任务提交 PR，QA 独立复核通过后，既有工程岗合并 PR 并核验 GitHub 自动部署；同一收尾任务由 QA 按整体验收线上复测，不再另建上线回归单。旧版已经派出的任务保留并等待完成。
- 产品可以补充已有仓库/CI/生产验证/回退说明，留空时从项目现有配置读取。合并不授予新的主机权限，也不绕过分支保护或保护命令；PR head 与已复核 SHA 不一致、必需检查失败、权限或流水线缺失时停止并报告阻塞。禁止手工构建/部署或另建构建/部署 Agent。GitHub Actions 与 Deployment 是当前可机器核验的生产证据来源，环境名为 `production`；其他发布平台需补验证适配器。
- 老板只需确认开工一次；删除二次确认发布命令和页面开关。旧版等待发布记录和 autoRelease=false 快照由新版执行端自动接续，审批历史不改写。原发布批准表保留审计，不再决定是否可合并。暂停与停用仍阻止推进。
- 合并与上线核验任务完成还不够：同一 SHA、同一提交尝试的 production GitHub 部署成功证据与独立 QA 线上验收必须齐全，才能写入 released 与 released_sha。CI 成功不能代替生产部署成功。
- 执行端每轮最多推进 5 个需求，每个需求一次只推进一个步骤。认领租期 120 秒，任务创建用需求/修订/步骤的固定业务键。重启与跨执行节点重试不会重复建单；消息恢复不会重新发送已经发送的执行/复核草稿。
- “暂停后续推进”不取消已经派出的任务或已经发起的部署。在推进临界区暂停会返回冲突，稍后重试。修改已确认范围应建立新的需求，不覆盖审批历史。

## 验证

`RUN_SCK_ITERATION_TESTS=1 bun test tests/product-iteration.test.ts tests/product-iteration.fork.test.ts` 使用公司 fork 的隔离临时库，覆盖真实 JWT 防代签、并发反馈、模型失败恢复、未确认不规划、暂停/重试、无二次审批、旧等待接续、独立复核门禁、错误 SHA/轮次/失败部署/缺少证据、完整公司 schema 的 core 租约/提交/独立评审与消息恢复。

测试中的发布证据为显式 fixture，仅验证状态机，不能作为真实生产上线证据。生产验证结果另行记录。

## 2026-11-10 生产验收

v0.9.0 已经主分支 CI、schema 063 迁移与 GitHub Release 发布，老板端和本机执行插件完成生产切换。专用测试产品 `iteration_verify` 的正式反馈组件提交成功；云端模型第一次整理生成待确认草稿，原文与分类理由可追溯。页面编辑后修订从 1 变成 2，未保存修改时确认按钮禁用；保存并确认后才建立规划。

需求 `feedback-2f508a1c76bc0ff1bb3c6f5acc30e3de9b26dcf8ea7df3288d6c79595c142aed` 修订 2 已暂停，测试产品停用，保留反馈、老板确认和任务记录。测试范围明确禁止仓库变更、合入和部署；已派出的只读核对任务继续按原租约执行。
